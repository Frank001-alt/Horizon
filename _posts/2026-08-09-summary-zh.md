### [酷 URI 永不变：W3C 经典文章的持久价值](https://www.w3.org/Provider/Style/URI) ⭐️ 8.0/10

hackernews · Klaster\_1 · 8月9日 14:32 · [社区讨论](https://news.ycombinator.com/item?id=49231809)

**「背景」** 在互联网早期，URL 的设计往往随意且易变，导致链接失效和资源丢失。作者 Tim Berners-Lee 指出，一个“酷”的 URI 应该是稳定、简洁且可预测的，能够长期指向同一资源，从而避免因链接断裂而造成的混乱。

**「方案」** 作者主张，设计 URI 时应像命名一个品牌一样慎重，避免包含易变的信息（如日期、版本号或技术细节），并确保即使内容迁移，旧 URI 也能通过重定向或保持原样继续工作。他强调，URI 是 Web 的基础设施，一旦发布，就应视为永久承诺。文章通过实例说明，糟糕的 URI 设计会导致用户和搜索引擎的困惑，而良好的 URI 设计则能提升可维护性和用户体验。尽管现代技术如 301 重定向和 CMS 内置的 slug 重命名功能缓解了部分问题，但作者的核心原则——在创建时规划一个稳定的 URI 体系——仍然适用。

**「启示」** 作者的核心论点是：URI 的持久性是 Web 可靠性的基石，设计者应从一开始就致力于创建“酷”URI，并承担起长期维护的责任。这一原则在近三十年后依然有效，提醒我们链接的稳定性关乎信息的可访问性和 Web 的完整性。

rss · Lobsters · 8月9日 23:06

**「背景」** Nix 的包管理器以其可复现构建而闻名，但 nixpkgs 仓库本身是不断演进的，用户通常只能访问当前或有限的版本。作者希望利用 Nix 存储的内容寻址特性，构建一个包含 nixpkgs 所有历史版本的“多元宇宙”，从而让任何历史版本都能被轻松获取和构建。

**「方案」** 作者的核心洞察是，Nix 存储中的每个构建产物都通过其内容的哈希来标识，因此不同版本的包可以共存而不会冲突。他设计了一个名为 nixpkgs-multiverse 的仓库，通过自动化脚本从 nixpkgs 的 Git 历史中提取每个提交，并为每个提交生成对应的 Nix 表达式，从而构建出所有历史版本的包。实现中，他利用了 Nix 的 flake 机制来组织这些版本，并解决了诸如依赖解析、版本冲突和存储空间管理等实际问题。作者还讨论了该方法的局限性，例如构建所有版本需要大量计算资源和时间，以及某些旧版本可能因依赖缺失而无法构建。尽管如此，他展示了如何通过内容寻址存储实现真正的可复现构建，并提供了具体的性能数据和示例。

**「启示」** 作者通过 nixpkgs-multiverse 证明了内容寻址存储不仅能实现可复现构建，还能解锁对历史版本的全面访问，为包管理和软件供应链的审计提供了新的可能性。
