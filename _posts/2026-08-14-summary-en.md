### [DRAM Attack Bypasses CPU Protections](https://github.com/xoreaxeaxeax/skitter-creek-bath-salts) ⭐️ 8.0/10

Security researcher Christopher Domas has released a proof-of-concept tool called &\#x27;skitter-creek-bath-salts&\#x27; that demonstrates a novel technique to bypass DRAM protections and achieve arbitrary code execution. The attack targets the AMD Jaguar architecture \(AMD16h\), a low-power CPU family from 2013, by manipulating DRAM timing and memory controller registers to gain access to hidden &\#x27;negative ring&\#x27; privileges. The README notes that Zen 3 has a different base address for memory controller registers, but it is unclear which newer CPUs are affected. This research highlights the growing attack surface in modern DRAM interfaces, which now require complex proprietary blobs and are difficult to understand. The findings have significant implications for system security and hardware design, though the specific impact on current systems remains uncertain.

hackernews · Lobsters · Aug 13, 14:17 · [Discussion](https://news.ycombinator.com/item?id=49286341)

**「Background」** Dynamic random-access memory \(DRAM\) stores each bit in a capacitor that leaks charge, so it must be periodically refreshed to retain data. Modern CPUs and memory controllers often apply address scrambling and encryption to DRAM traffic to obscure the physical layout of memory and protect against certain attacks. Christopher Domas&\#x27;s research, presented at Black Hat 2026, demonstrates a technique to reverse-engineer and bypass these DRAM scrambling protections, potentially allowing an attacker with ring-0 privileges to access hidden CPU features and achieve arbitrary code execution.

**「Impact」** On affected systems \(e.g., AMD Jaguar\), an attacker with ring-0 access can escalate to the highest privilege level, gaining full control over the system and bypassing protections like those in game consoles. The attack&\#x27;s applicability to newer CPUs is unclear, limiting immediate widespread impact.

**「Community Discussion」** Commenters express excitement for Domas&\#x27;s upcoming Black Hat talk, praising his ability to explain complex topics. Some note the historical simplicity of DRAM versus its current complexity, which contributes to the attack surface. Others speculate that console security teams \(Xbox, PlayStation\) may be concerned, while questioning the attack&\#x27;s relevance to newer architectures.

### [systemd-journald Log Line Causes 49KB+ Disk Writes](https://github.com/systemd/systemd/issues/40262) ⭐️ 8.0/10

A systemd issue reports that a single log line can cause 49KB+ of disk writes on ext4 and 110KB+ on btrfs due to journald&\#x27;s design. The issue highlights a significant performance problem in systemd-journald, a core component of most Linux systems, with concrete measurements. Community discussion criticizes journald&\#x27;s lack of filtering options and its tendency to accumulate large amounts of low-value log data. The report is valuable for system administrators and developers concerned with logging performance and storage efficiency.

hackernews · ValdikSS · Aug 13, 18:41 · [Discussion](https://news.ycombinator.com/item?id=49290215)

**「Background」** systemd-journald is the logging daemon of the systemd init system, which is used by most major Linux distributions. It collects log messages from the kernel and applications and stores them in a binary journal format, designed for robustness and atomicity using mmap-based access. The journal format appends data at the end of files, and each entry includes metadata fields, which can lead to significant disk write amplification. This issue is part of a long-standing concern about journald&\#x27;s performance, as evidenced by earlier reports such as issue \#15292 from 2020, which also noted excessive disk I/O.

**「Impact」** Users of systemd-based Linux distributions may experience increased disk I/O and storage consumption from journald, potentially affecting system performance and SSD lifespan, especially on systems with chatty applications or btrfs filesystems.

**「Community Discussion」** Commenters express frustration with journald&\#x27;s performance and lack of filtering, noting that applications often log excessively and that journald offers limited control over chatty subsystems. Some suggest using journald only as a router and forwarding logs to rsyslog for filtering, while others highlight the difficulty of filtering kernel messages.
